title: Configuration overview
description: How Mira splits configuration between per-repo .mira.yml and per-deployment environment variables.
---

Mira's configuration lives in two places. The split is intentional:

| Layer | File | Lifecycle | Holds |
| --- | --- | --- | --- |
| Per-repo | [`.mira.yml`](/configuration/mira-yml) | Committed to the repo | Review behaviour: which model, what to filter, how to walk through |
| Per-deployment | [Environment variables](/configuration/environment) | Set in your host (Docker, Fly, Railway, Render) | Secrets and infrastructure: GitHub App credentials, OpenRouter key, database URL |

When Mira reviews a PR, it walks up from the PR's working tree looking for a
`.mira.yml`. If it finds one, that file overrides the defaults. If it doesn't,
Mira uses sensible defaults out of the box.

## Decision tree

- **Need to change *what* gets reviewed and how strict it is?** → put it in
  [`.mira.yml`](/configuration/mira-yml).
- **Need to change *which* LLM Mira uses?** → either set `MIRA_MODEL` env var
  (deployment-wide default) or override per repo in `.mira.yml`.
- **Need to set credentials, database URL, or admin password?** → environment
  variables only — never put these in `.mira.yml` (it's committed).

## Precedence

For any given setting, Mira resolves in this order (highest priority first):

1. CLI overrides passed via `--override key=value` (rare; see the CLI docs for
   `mira review`).
2. Per-repo `.mira.yml` value.
3. Environment variable, if applicable (e.g. `MIRA_MODEL` overrides
   `llm.model`, `DATABASE_URL` overrides `database.url`).
4. Built-in defaults.
